# Feature 5: Bulk close

Status: planned. Final project.

## Goal

At the end of a sprint a team closes all finished work in a project with one request.

## API

`POST /projects/{project_id}/issues/bulk-close` with `{"issue_ids": [...]}` returns 200 and

```json
{"closed": [3, 7], "skipped": [{"id": 5, "reason": "invalid_transition"}]}
```

- `issue_ids` holds 1 to 100 distinct positive integers. An empty list, more than 100 ids, a repeated
  id, or a non-integer gives 422 `validation_error`. The body is validated before any id is looked
  up: an invalid body gives 422 even when it also names unknown or foreign ids.
- Atomic: if any id is not a live issue of that project in the caller's org (another project's issue,
  another org's issue, a deleted issue, an unknown id), the response is 404 `not_found` and nothing
  changes.
- Status rules come from HANDBOOK "Issues": only `in_progress` may move to `done`. Such an issue is
  closed: its status becomes `done` and its `version` goes up by one. An issue that is already `done`
  is skipped with reason `already_done`; an `open` issue is skipped with reason `invalid_transition`
  and stays open.
- `closed` and `skipped` keep the order of `issue_ids`. Every id appears in exactly one of them.
- Another org's project or an archived project gives 404. Viewers get 403 `forbidden`.
- One audit row per successful request, even when every issue is skipped: action `issue.bulk_close`,
  entity `project`, entity id the project's id. A refused request adds none.
- The request does not need `If-Match`.

## Out of scope

Bulk changes other than closing, closing across projects.
